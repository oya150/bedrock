# 빅오는 왜 필요한가

## 테스트에서는 1밀리초였다

회원 목록에서 탈퇴한 회원만 골라내는 코드가 있다고 하자. 처음 떠오르는 대로 쓰면 이렇다.

```python
def withdrawn_slow(members, withdrawn):
    out = []
    for m in members:          # 회원마다
        for w in withdrawn:    # 탈퇴 목록을 처음부터 끝까지 보며
            if m == w:
                out.append(m)
    return out
```

회원 1,000명, 탈퇴자 100명으로 돌려 보면 1밀리초가 안 걸린다. 테스트는 통과했고 리뷰에서도 아무도 문제 삼지 않는다. 그런데 회원이 100만 명이고 탈퇴자도 같은 비율인 10만 명인 운영 서버에 올리면, 이 함수 하나가 14분쯤 걸린다.

## 시계로 재면 안 될까

가장 먼저 드는 생각은 직접 재 보는 것이다. 같은 노트북에서 백만 개를 더하는 반복문을 다섯 번 재면 이렇게 나온다.[^lab]

| 1회 | 2회 | 3회 | 4회 | 5회 |
|---|---|---|---|---|
| 17.2 ms | 17.1 ms | 17.4 ms | 17.0 ms | 17.3 ms |

한 기계 안에서는 꽤 고르니 시계가 쓸모없지는 않다. 잴 때는 같은 크기에서 여러 번 재 가장 작은 값을 쓰는 게 좋다. 다른 프로그램이 끼어들면 측정은 느려질 수는 있어도 빨라질 수는 없으니, 가장 작은 값이 코드 자체에 드는 시간에 가장 가깝다. 그런데 이 숫자로는 다른 기계에서 얼마나 걸릴지 모른다. CPU, 파이썬 버전, 그 순간 다른 프로그램이 무엇을 하는지에 따라 달라진다.

더 곤란한 건 데이터가 늘었을 때를 모른다는 점이다. 탈퇴 회원 코드는 회원 1,000명에서 0.9밀리초였다. 100만 명이면 900밀리초일까, 그보다 훨씬 클까. 숫자 하나로는 답이 안 나온다.

그래서 시간 하나보다 **데이터를 두 배로 늘렸을 때 시간이 몇 배가 되는지**를 본다. 탈퇴자를 늘 회원의 10%로 두고 늘려 보면 이렇다.

| 회원 수 | 느린 코드 | 전보다 | 빠른 코드(뒤에 나옴) | 전보다 |
|---|---|---|---|---|
| 1,000 | 0.94 ms | | 0.016 ms | |
| 2,000 | 3.54 ms | 3.8배 | 0.034 ms | 2.1배 |
| 4,000 | 13.27 ms | 3.7배 | 0.063 ms | 1.9배 |
| 8,000 | 52.97 ms | 4.0배 | 0.144 ms | 2.3배 |

느린 코드는 회원이 두 배가 될 때마다 거의 네 배가 된다. 빠른 기계는 표의 모든 칸을 똑같이 줄일 뿐이라, 두 배일 때 네 배라는 관계는 기계를 바꿔도 남는다.

## 시간 대신 횟수를 센다

매번 데이터를 만들어 돌려 볼 수는 없으니, 코드만 보고 알 방법이 필요하다. 횟수를 세면 된다. 한 번에 걸리는 시간은 기계마다 달라도 같은 일을 몇 번 하는지는 코드가 정한다.

무엇을 한 번으로 셀지부터 정한다. 기준은 전체 시간을 대부분 차지하는 일이다. 보통은 가장 안쪽 반복에서 하는 일이 그렇다. 탈퇴 회원 코드에서는 `m == w`, 회원 하나와 탈퇴자 하나를 맞대 보는 비교다. 이것을 한 번으로 센다.

회원이 \(n\)명이고 탈퇴자가 그 10%인 \(n/10\)명이면, 바깥 반복이 \(n\)번, 그 안쪽이 매번 \(n/10\)번 돈다.

\[
\text{비교 횟수} = n \times \frac{n}{10} = \frac{n^2}{10}
\]

회원이 두 배면 \(\frac{(2n)^2}{10} = 4 \times \frac{n^2}{10}\), 네 배다. 앞의 실측과 맞는다. 회원 8,000명이면 640만 번, 100만 명이면 1,000억 번이다. 8,000명에서 53밀리초였으니 회원이 125배인 100만 명에서는 \(125^2 = 15{,}625\)배, 약 830초다. 처음에 말한 14분이 이 계산이다. 거꾸로 나눠 보면 비교 한 번에 53밀리초 ÷ 640만 번, 약 8나노초가 든 셈이다. 운영에서도 탈퇴자가 늘 100명뿐이라면 이야기가 달라진다. 그때는 안쪽 반복이 고정이라 회원 수만큼만 늘고, 1초 안팎이다.

빠른 코드는 탈퇴 목록을 `set`에 한 번 담아 두고 회원마다 한 번씩만 묻는다.

```python
def withdrawn_fast(members, withdrawn):
    gone = set(withdrawn)                        # 탈퇴자 수만큼 한 번씩
    return [m for m in members if m in gone]     # 회원 수만큼 한 번씩
```

`set`에 묻는 일은 한 번으로 친다.[^set] 그러면 횟수는 \(n/10 + n\)이고, 두 배면 두 배다. 표에서 본 2배 안팎이 이것이다. 100만 명이면 8,000명일 때의 125배인 18밀리초쯤이다.

`set` 대신 리스트에 `m in withdrawn`으로 물었다면 이야기가 다르다. 겉으로는 한 줄이지만 리스트의 `in`은 안에서 처음부터 끝까지 도는 반복이라, 느린 코드와 같은 \(n^2/10\)번이 된다. 이런 반복은 이중 `for`보다 눈에 덜 띄어서 리뷰에서 더 자주 놓친다.

## 식에서 모양만 남긴다

실제 코드를 세면 식이 이렇게 깔끔하지 않다. 반복문 앞뒤로 준비하는 일이 붙고, 조건에 따라 한 번 더 하는 일이 생긴다. 어떤 코드를 꼼꼼히 셌더니 \(3n^2 + 5n + 2\)가 나왔다고 하자. 데이터가 늘 때를 판단하려고 이 식을 다 들고 다닐 필요는 없다.

| \(n\) | \(3n^2\) | \(5n + 2\) | 전체에서 \(3n^2\)이 차지하는 몫 |
|---|---|---|---|
| 10 | 300 | 52 | 85% |
| 1,000 | 3,000,000 | 5,002 | 99.8% |
| 1,000,000 | 3,000,000,000,000 | 5,000,002 | 99.9998% |

\(n\)이 커질수록 \(5n + 2\)는 없는 것과 같아진다.

남은 \(3\)도 뗄 수 있다. 두 배가 되면 몇 배인지를 물으면 \(\frac{3(2n)^2}{3n^2} = 4\)로, 앞의 3은 나눗셈에서 지워진다.

이렇게 가장 빨리 자라는 항만 남기고 앞의 숫자를 뗀 것을 빅오로 쓴다. \(3n^2 + 5n + 2\)는 \(O(n^2)\)이고, 탈퇴 회원의 빠른 코드 \(1.1n\)은 \(O(n)\)이다.

자주 만나는 모양을 자라는 빠르기 순으로 놓으면 \(1 < \log n < n < n \log n < n^2\)이다. 맨 앞의 1은 데이터가 늘어도 횟수가 그대로인 일로, `set`에 한 번 묻는 일이 여기에 든다.

\(\log_2 n\)은 2를 몇 번 곱해야 \(n\)이 되는지를 센 값이다.[^log] \(2^{10} = 1{,}024\)이니 \(\log_2 1{,}000\)은 10쯤이고, \(2^{20}\)은 약 105만이니 \(\log_2 1{,}000{,}000\)은 20쯤이다. \(n\)이 1,000배가 되어도 \(\log n\)은 두 배밖에 안 된다. \(n\)이 두 배가 되면 2를 한 번 더 곱한 것이니 \(\log n\)은 1만 는다. 그래서 \(n \log n\)은 \(n\)보다 아주 조금 더 빨리 자란다. \(n\)이 1,000에서 2,000이 되면 \(\frac{2{,}000 \times 11}{1{,}000 \times 10} = 2.2\)배다.

??? note "정확한 정의"
    \(f(n) = O(g(n))\)은 어떤 양수 \(c\)와 \(n_0\)가 있어서 \(n \ge n_0\)인 모든 \(n\)에 대해 \(f(n) \le c \cdot g(n)\)이라는 뜻이다. 말로 하면 "\(n\)이 어느 크기를 넘으면 \(f\)는 \(g\)의 몇 배를 넘지 않는다"다.

    \(3n^2 + 5n + 2\)라면 \(c = 4\)로 잡아 본다. 그러면 \(5n + 2 \le n^2\)이 성립해야 하는데, \(n\)에 차례로 넣어 보면 \(n = 5\)에서는 \(27 > 25\)라 안 되고 \(n = 6\)에서 \(32 \le 36\)으로 처음 성립한다. 그 뒤로도 계속 성립한다. \(n\)이 1 늘 때 \(n^2\)은 \(2n + 1\)만큼 늘고 \(5n + 2\)는 5만큼 느는데, \(n \ge 6\)이면 \(2n + 1\)이 5보다 크니 한 번 앞선 \(n^2\)이 다시 뒤처지지 않는다. 그래서 \(n_0 = 6\)이다.

## n이 충분히 클 때만 맞는 이야기

작은 항과 앞의 숫자를 버려도 되는 건 \(n\)이 클 때뿐이다. 그러니 판단할 때는 버린 것들이 실제로 작은지를 따지면 된다.

### 앞의 숫자가 클 때

반복문으로 합을 구하는 코드와 내장 함수 `sum`은 둘 다 원소를 하나씩 한 번 본다. 둘 다 \(O(n)\)이다. 그런데 재 보면 이렇다.

| \(n\) | `for`로 더하기 | `sum` | 차이 |
|---|---|---|---|
| 100,000 | 1.60 ms | 0.32 ms | 5.0배 |
| 1,000,000 | 17.64 ms | 3.83 ms | 4.6배 |

빅오가 같아도 다섯 배가 차이 난다. `for` 반복은 파이썬이 한 줄씩 해석하며 돌고, `sum`은 C로 짠 반복이 돈다. 걸리는 시간은 한 번에 드는 비용에 횟수를 곱한 것이다. 그러니 한 번 비용도 \(3n^2\)의 3처럼 앞에 곱해지는 숫자로 작용하고, 빅오는 그런 숫자를 뗐으니 둘을 구별하지 못한다.

### n이 작을 때

이번에는 빅오가 다른 둘을 작은 데이터에서 견준다. 삽입정렬은 앞에서부터 하나씩 꺼내 이미 정리한 쪽의 제자리에 끼워 넣는 방법이다. 끼울 때 그 뒤 원소를 한 칸씩 밀어야 해서 \(i\)번째 원소는 최악의 경우 \(i\)번 일한다. \(1 + 2 + \cdots + n\)은 \(n^2/2\)쯤이니 \(O(n^2)\)이다. 병합정렬은 반씩 나눠 각각 정렬한 뒤 합치는 방법이고 \(O(n \log n)\)이다. 몇 번 반으로 나눠야 1이 되는지는 2를 몇 번 곱해야 \(n\)이 되는지와 같은 질문이라 \(\log n\)번이고, 정렬된 두 묶음을 합칠 때는 맨 앞끼리 비교해 작은 쪽을 꺼내는 일을 되풀이하니, 두 묶음 길이의 합만큼 일한다. 한 단계의 조각들을 다 더하면 원소 \(n\)개이니 단계마다 \(n\)번이고, 단계가 \(\log n\)개라 \(n \log n\)이다. 둘 다 순수 파이썬으로 짜서 같은 조건으로 쟀다.

| \(n\) | 삽입정렬 | 병합정렬 | 빠른 쪽 |
|---|---|---|---|
| 8 | 0.9 µs | 3.9 µs | 삽입 |
| 32 | 9.4 µs | 20.4 µs | 삽입 |
| 64 | 34.2 µs | 44.5 µs | 삽입 |
| 128 | 121.8 µs | 97.3 µs | 병합 |
| 1,024 | 10,837 µs | 975 µs | 병합 |

64개까지는 \(O(n^2)\)인 삽입정렬이 이긴다. 병합정렬은 나누고 합치는 준비가 많아 한 번에 드는 비용이 크다. 그래서 \(n\)이 64와 128 사이를 넘어서야 병합정렬이 더 빨라진다.

표의 비율이 이론값과 딱 맞지는 않는다. 삽입정렬이 \(n^2\)이면 128에서 1,024로 8배 늘 때 64배가 되어야 하는데 실제로는 89배였고, 8에서 32로 갈 때는 16배 대신 10배였다. 작은 쪽은 함수를 부르는 것 같은 고정 비용이 섞여 덜 는 것으로 보인다. 큰 쪽이 더 는 이유는 따로 확인하지 않았다.

파이썬도 실제로 이렇게 한다. `list.sort`는 원소가 64개보다 적으면 병합 없이 이진 삽입정렬 하나로 배열 전체를 정렬한다.[^listsort] 이진 삽입정렬은 끼울 자리를 반씩 좁혀 찾는 삽입정렬이다. 자리를 빨리 찾아도 뒤 원소를 미는 일은 그대로라 여전히 \(O(n^2)\)이다.

### 센 일 말고 다른 일이 시간을 먹을 때

빅오는 센 일 하나하나에 드는 시간이 비슷하다고 치고 계산한다. 반복문 안에서 데이터베이스나 다른 서버를 부르면 이 전제가 깨진다. 비교 한 번은 나노초 단위인데 네트워크 왕복 한 번은 밀리초 단위라, 한 번의 무게가 백만 배쯤 다르다. 그래서 여기서는 비교 대신 왕복을 센다.

## 판단 연습

??? question "1. 테스트에서 2밀리초, 운영에서는?"
    상품 1,000개로 테스트했을 때 세 함수가 모두 2밀리초였다. 운영 데이터는 100만 개다. 함수 A는 \(O(n)\), B는 \(O(n \log n)\), C는 \(O(n^2)\)이다. 각각 대략 얼마나 걸릴까.

    **풀이**
    데이터가 1,000배다.

    - A는 1,000배라 2초쯤.
    - B는 1,000배에, \(\log n\)이 \(\log 10^6 / \log 10^3 = 2\)배가 되어 4초쯤. 로그의 밑을 무엇으로 잡든 나눗셈에서 지워지니 신경 쓰지 않아도 된다.
    - C는 \(1{,}000^2 = 100\)만 배라 2,000초, 약 33분.

    다만 이 계산은 1,000개가 이미 "충분히 큰 \(n\)"이라고 보고 곱한 것이다. 1,000개에서 잰 시간에 준비 비용이 많이 섞여 있었다면 예측이 빗나간다. 확실히 하려면 문제 4번처럼 두세 크기에서 재 보고 늘어나는 비율이 자리를 잡았는지 확인한다.

??? question "2. 설정 항목 중복 검사"
    서비스 설정 파일에는 항목이 30개 안팎이고 앞으로도 크게 늘 일이 없다. 중복 이름을 찾는 코드가 이중 반복문(\(O(n^2)\))으로 되어 있다. 고쳐야 할까.

    **풀이**
    30개면 비교가 900번 안쪽이다. 탈퇴 회원 코드에서 비교 한 번이 8나노초쯤이었으니 900번이면 7마이크로초 남짓이다. 데이터가 커지지 않으니 지금 코드가 읽기 쉽다면 그대로 두는 편이 낫다. 항목이 사용자 입력처럼 늘어날 수 있는 데이터라면 판단이 바뀐다.

??? question "3. 주문마다 회원 정보를 조회하는 코드"
    주문 목록 페이지가 주문 \(n\)건을 돌며 주문마다 회원 정보를 데이터베이스에서 한 번씩 조회한다. 코드는 \(O(n)\)이다. 주문을 한 번에 모아 조회하는 방식으로 바꾸자는 의견이 나왔는데, 그 방식도 결국 \(n\)건을 다루니 \(O(n)\)이다. 빅오가 같으니 바꿀 필요가 없을까.

    **풀이**
    여기서 셀 건 데이터베이스 왕복이다. 앞의 방식은 왕복이 \(n\)번이고, 뒤의 방식은 한 번이다. 왕복 한 번이 2밀리초라면 주문 1,000건에서 앞의 방식은 왕복에만 2초를 쓴다. 모아 조회하는 쿼리도 데이터베이스 안에서 1,000건을 다루지만, 그 일은 대개 데이터베이스 안에서 빠르게 끝나 왕복 한 번에 비하면 작다. 감이 안 오면 둘 다 한 번 재 보면 된다.

??? question "4. 코드가 복잡해서 셀 수 없을 때"
    여러 함수를 거치는 코드라 몇 번 도는지 세기 어렵다. 빅오를 어떻게 짐작할까.

    **풀이**
    데이터를 늘려 가며 잰다. 두 배씩 늘리면 \(O(n)\)은 2배, \(O(n \log n)\)은 2.2배쯤, \(O(n^2)\)은 4배다.

    그런데 2배와 2.2배는 측정 흔들림에 묻힌다. 앞의 빠른 코드는 \(O(n)\)인데 두 배마다 1.9배에서 2.3배 사이를 오갔고, 1,000명에서 8,000명까지 통째로 보면 9배였다. 이론으로는 \(O(n)\)이 8배, \(O(n \log n)\)이 10배 남짓이니 딱 그 사이다. 실측만으로 둘을 가리기는 어렵다.

    다행히 업무 판단에서는 둘을 가릴 일이 드물다. \(\log n\)은 100만에서도 20쯤이라 둘 다 데이터만큼 느는 코드로 보면 된다. 실측으로 꼭 잡아야 하는 건 \(n^2\)이다. 느린 코드는 같은 구간에서 56배였다.

## 더 들어가기

### 이 표기는 어디서 왔나

\(O\)는 컴퓨터보다 먼저 나왔다. 독일 수학자 파울 바흐만이 1894년 정수론 책에서 처음 썼고, 에드문트 란다우가 1909년 책에서 이를 받아 쓰면서 "훨씬 작다"를 뜻하는 소문자 \(o\)를 더해 널리 퍼뜨렸다.[^history] 소문자 \(o\)는 여기서 쓰지 않는다. 쓰임새는 \(1 + 2 + \cdots + n = \frac{n^2}{2} + O(n)\)처럼, 근사한 값 뒤에 남는 나머지가 많아 봐야 어느 크기의 몇 배라고 적는 것이었다. 그러니 \(O\)는 처음부터 위쪽 한계를 나타냈다. \(O\)는 독일어로 차수를 뜻하는 Ordnung에서 왔다.

계산에 드는 시간을 입력 크기의 함수로 따지는 연구는 1960년대에 자리를 잡았다. 유리스 하르트마니스와 리처드 스턴스가 1965년에 낸 논문 「On the Computational Complexity of Algorithms」가 이 분야를 연 논문으로 꼽히고, 두 사람은 이 일로 1993년 튜링상을 받았다.[^hs]

1976년 도널드 크누스는 학회 소식지에 쓴 짧은 글에서, 사람들이 \(O\)를 아래쪽 한계를 말할 때도 쓰는 혼란을 지적하고 \(\Omega\)와 \(\Theta\)를 알고리즘 분석에 맞게 정리했다.[^knuth]

### O, Ω, Θ

- \(O(g)\): 위쪽 한계. 많아 봐야 \(g\)의 몇 배다.
- \(\Omega(g)\): 아래쪽 한계. 적어도 \(g\)의 몇 배다.
- \(\Theta(g)\): 둘 다. \(g\)와 같은 빠르기로 자란다.

엄밀히 하면 \(O(n)\)인 코드는 \(O(n^2)\)이기도 하다. \(n\)은 \(n^2\)을 넘지 않으니까. 개발자들이 "이 코드는 \(O(n)\)이다"라고 할 때는 대개 \(\Theta(n)\), 딱 \(n\)의 빠르기로 자란다는 뜻이다. 이 글도 그 관습을 따른다.

### 최악의 경우와 평균, 나눠 내기

앞의 탈퇴 회원 코드는 입력이 어떻든 횟수가 같았다. 대부분의 코드는 그렇지 않다. 찾는 값이 맨 앞에 있으면 한 번에 끝나고 맨 끝에 있으면 끝까지 본다. 그래서 빅오를 말할 때는 보통 최악의 경우를 말한다. 최악과 평균은 어떤 입력을 놓고 셀지를 정하는 것이고, \(O\)와 \(\Theta\)는 그렇게 센 횟수가 어떻게 자라는지 적는 표기다. 둘은 따로 고르는 것이라 "최악의 경우 \(\Theta(n)\)"처럼 함께 쓸 수 있다. 어떤 일은 가끔 크게 비싸지만 길게 보면 한 번에 조금씩 나눠 내는 셈이 되기도 하는데, 파이썬 `list.append`가 그렇다. 칸이 다 차면 더 큰 자리를 잡아 전부 옮기느라 그 한 번은 비싸지만, 넉넉하게 늘려 두기 때문에 그런 일이 드물게 일어난다. 자세한 건 `list` 편에서.
